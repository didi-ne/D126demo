# D126 BLE 推图协议

版本：1.0  
日期：2026-09-15  
适用：手机 APP ↔ D126 板端 SDK（Luban-Lite）  
范围：只把一张 **360×360 JPEG** 推到 **QSPI 屏**（T180BV / `qspi1`）。MIPI 视频屏不走本协议。

名词：

- **GATT**（Generic Attribute Profile）：BLE 的服务/特征模型，本协议全部走 GATT，没有经典蓝牙 / SPP。
- **Characteristic**（特征）：GATT 里一块可写/可通知的数据，下文 CTRL / DATA / STATUS 都是特征。
- **ATT MTU**（Attribute Protocol Maximum Transmission Unit）：一次 ATT 包的最大长度。协商到 247 后，Write 有效载荷 = `MTU − 3 = 244` 字节。
- **Write Request**：带 ATT 应答的写，用于 START。
- **Write Without Response（WWR）**：无 ATT 应答的写，吞吐高但会丢包，用于 MIDDLE / END。
- **Notify**：板端主动推给手机的通知，用于 STATUS。
- **CRC-32/ISO-HDLC**：多项式 `0xEDB88320`，init `0xFFFFFFFF`，xorout `0xFFFFFFFF`，与 zlib / PNG 相同。SDK 用 `aic_crc32`。

## 1. 约束（按 D126 性能锁死）

| 项 | 值 | 原因 |
|----|----|------|
| 芯片 | D126，CPU E907 480 MHz | CRC / 组包不是瓶颈 |
| 片内 SRAM | 约 20 KB | JPEG **禁止**放 SRAM |
| 收图缓冲 | PSRAM | 当前方案 SW heap 2 MB，够用 |
| 目标屏 | 360×360，JPEG only | 解码输出 RGB565 = 259200 B，放 PSRAM |
| 整图上限 | **96 KB**（98304） | 360×360 q70–80 约 20–50 KB，q90 偶发 80 KB |
| ATT MTU | **247** | 手机 `requestMtu(247)`；MTU &lt; 100 直接失败 |
| 单包上限 | **244 B**（`MTU − 3`） | 超过会被 BLE 栈截断 |
| 单包 JPEG 负载 | **232 B** | 见 DATA 包格式，总长 241 B ≤ 244 |
| 窗口 | **8 包** ≈ 1856 B JPEG | WWR 无 ATT 重传；8800 HCI UART 默认 921600，连发会打满 ACL 缓冲 |
| 失败策略 | **整图重传** | 不做选择性重传 |
| HCI | CPU **UART3** 内部键合 8800 | 封装无 UART3 球，pinmux 不配 GPIO |

一次空口只发 1 个 ATT 包。不要把整张图一次性 WWR 灌进去。

## 2. 常量（APP / SDK 必须一致）

```
广播名                XMZX-D126

Service UUID          0000FF00-0000-1000-8000-00805F9B34FB
CTRL    UUID          0000FF01-0000-1000-8000-00805F9B34FB
DATA    UUID          0000FF02-0000-1000-8000-00805F9B34FB
STATUS  UUID          0000FF03-0000-1000-8000-00805F9B34FB

BLE_IMG_MTU           247
BLE_IMG_CHUNK_PAYLOAD 232
BLE_IMG_WIN           8
BLE_IMG_MAX           98304
BLE_IMG_W             360
BLE_IMG_H             360
BLE_IMG_FMT_JPEG      0

FLAG_START            0x01
FLAG_MIDDLE           0x02
FLAG_END              0x03

MAGIC                 "IMGP"   /* 49 4D 47 50 */
```

字节序：**小端（little-endian）**。

## 3. GATT 角色

| UUID | 名称 | 权限 | 谁写 | 内容 |
|------|------|------|------|------|
| `FF00` | Service | — | — | 推图服务 |
| `FF01` | CTRL | Write Request | APP | **只发 START** |
| `FF02` | DATA | Write Without Response | APP | **只发 MIDDLE / END** |
| `FF03` | STATUS | Notify | 板 | 5 字节状态 |

连接后顺序：

1. 扫描广播名 `XMZX-D126`
2. 连接
3. `requestMtu(247)`，并走 DLE（Data Length Extension，空口 PDU 拉到约 251 B）
4. 发现 Service `FF00`
5. 使能 STATUS Notify
6. 再发 START

## 4. 包格式

### 4.1 Flag（包类型）

`flag` 是 **1 字节无符号整数**，告诉板端「这是一帧的开始、中间还是结尾」。不是布尔，也不是 ASCII 字符。

| 本协议取值 | 名 | 走哪条特征 | seq | 含义 |
|------------|----|------------|-----|------|
| `0x01` | START | CTRL | 固定 0 | 开始一张图，带元数据 + 整图 CRC，**无 JPEG 负载** |
| `0x02` | MIDDLE | DATA | 1 … `chunk_cnt−1` | 中间分片，`plen` 必须为 232 |
| `0x03` | END | DATA | `chunk_cnt` | 最后一片，`plen` 为剩余字节（整除则为 232） |

`chunk_cnt = ceil(total_len / 232)`，**不含 START**。第一片 JPEG 的 seq=1。最后一片无论长短，flag 必须是 `END`。只有一片时（`total_len ≤ 232`）直接发 END，seq=1，没有 MIDDLE。

其它值不要填：

| 值 | 为什么不用 |
|----|------------|
| `0x00` | 未初始化内存常见值，板端无法区分「没填」和「合法类型」，保留不用 |
| `0x04` | 预留，以后若要做 ABORT（取消本张图）可以用，当前当 `FLAG_ERR` |
| `0x05`～`0xFF` | 未定义，当前当 `FLAG_ERR` |

不要把 flag 写成字符 `'S'`/`'M'`/`'E'`（`0x53/0x4D/0x45`），板端按数值比，不是按字母。

### 4.2 START（CTRL，固定 26 字节）

START 只走 CTRL（Write Request）。26 字节全部是元数据，**后面不要再拼 JPEG**。板端先验 `crc_pkt`，再验 magic / 尺寸 / 宽高 / fmt；通过则 Notify `OK`（`value` = 窗口 8），忙则 `BUSY`。

| 偏移 | 长度 | 字段 | 本协议必须填 | 编码 |
|------|------|------|--------------|------|
| 0 | 1 | `flag` | `0x01` | uint8 |
| 1 | 2 | `seq` | `0` | uint16 LE |
| 3 | 4 | `magic` | `"IMGP"` | 4 字节 ASCII，不是 C 字符串 |
| 7 | 4 | `total_len` | 本次 JPEG 文件字节数 | uint32 LE，1…98304 |
| 11 | 2 | `width` | `360` | uint16 LE，像素 |
| 13 | 2 | `height` | `360` | uint16 LE，像素 |
| 15 | 1 | `fmt` | `0` | uint8，像素格式代号 |
| 16 | 2 | `chunk_cnt` | `ceil(total_len / 232)` | uint16 LE，DATA 包个数 |
| 18 | 4 | `crc_file` | 整份 JPEG 的 CRC32 | uint32 LE |
| 22 | 4 | `crc_pkt` | 本包 offset 0…21 共 22 字节的 CRC32 | uint32 LE |

下面按字段说明：**这个值是什么、为什么锁死、还能填什么（当前填了板端会拒）**。

#### `flag`（偏移 0，1 字节）

本包类型。START 固定填 **`0x01`**。填 `0x02`/`0x03` 到 CTRL 算顺序错误，`FLAG_ERR`。见 4.1。

#### `seq`（偏移 1，2 字节）

分片序号，从 0 起的 **uint16 小端**。START 固定填 **`0x0000`（十进制 0）**，表示「这不是 JPEG 分片，是会话头」。

- 写成 `00 00`，不要写成 ASCII `"0"`（`0x30`）或浮点。
- JPEG 分片从 **1** 开始，给 `buf[(seq-1)*232]` 用；若 START 也占 seq=1，第一片 JPEG 会和头冲突，所以头单独占 0。
- 不要填 `0xFFFF` 当「无效」。u16 合法范围 0…65535，96 KB 最多约 414 个 DATA 包，远小于 65535。
- 重传整张图时 START 仍填 0，不要把上次的 seq 带过来。

#### `magic`（偏移 3，4 字节）

协议魔数（magic number，用来识别「这是推图 START，不是随便写到 CTRL 的垃圾」）。固定 4 个 ASCII 字符 **`IMGP`**（Image Push）：

| 字符 | hex |
|------|-----|
| `I` | `0x49` |
| `M` | `0x4D` |
| `G` | `0x47` |
| `P` | `0x50` |

线上顺序：`49 4D 47 50`。

- **不是** C 字符串，末尾 **不要** 加 `'\0'`。加了会把 `total_len` 挤乱。
- **不要** 填 `"JPEG"`（`4A 50 45 47`）。那是格式名，容易和文件头 `FF D8` 搞混；板端只认 `IMGP`。
- **不要** 填 `"IMG"` + 空格、`"imgp"` 小写、Unicode。大小写必须完全一致。
- 其它 4 字节（如 `0xA5A5A5A5`、`"AIC1"`）理论上都能当魔数，但 APP/SDK 已锁 `IMGP`，填别的一律当 `FLAG_ERR`。
- 作用：拒绝其它 BLE 调试 App 误写 CTRL、拒绝半截包、拒绝把 JPEG 文件头当 START。

#### `total_len`（偏移 7，4 字节）

**压缩后 JPEG 文件**的字节数，不是原图像素宽×高，也不是加协议头之后的总流量。

- 合法：**1…98304**（96 KB）。例：500 字节写成 `F4 01 00 00`。
- 填 **0**：空图，`SIZE_ERR`。
- 填 **>98304**：板端 PSRAM 策略按 96 KB 封顶，`SIZE_ERR`。APP 应降 JPEG quality 再压，而不是把原图 2 MB 填进来。
- 必须 **等于** 后面所有 DATA 的 `plen` 之和，也必须等于 `crc_file` 所覆盖的那份 buffer 长度。多 1 字节或少 1 字节都会在 END 时对不上。
- 不要填解码后 RGB565 大小（360×360×2=259200），那不是传输长度。

#### `width` / `height`（偏移 11 / 13，各 2 字节）

图的像素宽高，**小端 uint16**。本协议固定 **360 / 360**，hex：`68 01`、`68 01`（360=0x0168）。

- 这是 **QSPI 屏 T180BV 的物理分辨率**，不是手机相册原图尺寸。APP 必须先缩放/裁剪到 360×360 再压 JPEG。
- 填 `1920×1080`、`720×1280`（MIPI 屏尺寸）都会被板端 `SIZE_ERR`。MIPI 不走本协议。
- 填 `0×0` 非法。
- 以后若换别的圆屏，可以改这两个数，但必须同步改 SDK 校验和 LVGL 控件大小；**当前版本禁止填其它值**。
- 宽高只用于板端校验「APP 是否按屏准备」，解码仍以 JPEG 内部 SOF（Start of Frame，JPEG 里记录真实宽高的标记）为准。当前要求：**START 的宽高、JPEG SOF 宽高、屏幕，三者都是 360**。SOF 不是 360 时丢图，回 `SIZE_ERR`。

#### `fmt`（偏移 15，1 字节）

像素/封装格式代号，**不是** MIME 字符串，**不要** 填 `"jpeg"` 或 `0xFF 0xD8`。

| 值 | 含义 | 本版本 |
|----|------|--------|
| **`0x00`** | JPEG / MJPEG（文件以 `FF D8` 开头，走 VE / `lv_mpp_dec`） | **唯一合法** |
| `0x01` | RGB565 原始像素，360×360×2=259200 B | 未实现。超过 96 KB 上限，BLE 太慢，填了 `SIZE_ERR` |
| `0x02` | PNG | 未实现，无对等硬件解码路径 |
| `0x03` | AICP（匠芯创内部图格式） | 未实现 |
| `0x04`～`0xFF` | 保留 | `SIZE_ERR` |

选 JPEG 而不是 RGB565：同样 360×360，JPEG q80 大约 20–50 KB，RGB565 固定 254 KB，BLE 窗口传输要多几倍时间，且 `BLE_IMG_MAX` 装不下。

APP 侧用系统编码器时：baseline JPEG（SOF0），不要用渐进式 JPEG（SOF2），VE 不一定收。

#### `chunk_cnt`（偏移 16，2 字节）

后面要发多少个 **DATA 包**（MIDDLE+END 的总数），**不含 START**。

```
chunk_cnt = ceil(total_len / 232)
```

例：`total_len=500` → `ceil(500/232)=3`，写成 `03 00`。

- 这是 **算出来的**，不能随便填 1 或 8。填错板端 `SIZE_ERR`（用来抓 APP 除法写错、忘了向上取整）。
- 不要填窗口大小 8。8 是每窗最多发几包，和一张图总共几包不是一回事。
- `total_len=232` → `chunk_cnt=1`（只有 END）。
- `total_len=233` → `chunk_cnt=2`（1 个 MIDDLE + 1 个 END）。
- 理论上可改成「不传、板端自己算」，本协议选择显式带上，两边对账。

#### `crc_file`（偏移 18，4 字节）

对 **完整 JPEG 文件**（从 `FF D8` 到文件末尾，不含任何 START/DATA 头）做 CRC32，小端写入。

- 必须是算出来的值，**禁止**填 `00 00 00 00` 当「不校验」。真文件 CRC 碰巧为 0 极罕见；板端仍会按算法比对。
- 不要对「带协议头的整段蓝牙数据」做 CRC，也不要对 RGB565 做。
- 算法见第 9 节。APP 和 SDK 必须同一套（zlib / ISO-HDLC），不要用 CRC-32C（Castagnoli）或 MPEG-2 那种变体。

#### `crc_pkt`（偏移 22，4 字节）

只保护 **本 START 包前 22 字节**（flag … crc_file），不含这 4 字节自己。

- 组包顺序：先填 0…21，再算 CRC，再写入 22…25。
- 填 0 跳过校验：**不允许**。
- 和 `crc_file` 不是同一个数。一个管会话头有没有传错，一个管整图有没有少字节。

### 4.3 MIDDLE / END（DATA）

走 DATA 特征，Write Without Response。JPEG 正文只出现在这里。

| 偏移 | 长度 | 字段 | 本协议必须填 |
|------|------|------|--------------|
| 0 | 1 | `flag` | MIDDLE=`0x02` 或 END=`0x03` |
| 1 | 2 | `seq` | 1 … `chunk_cnt`，uint16 LE，连续递增 |
| 3 | 2 | `plen` | 本包 JPEG 字节数，uint16 LE |
| 5 | `plen` | payload | JPEG 原文切片，按文件顺序 |
| 5+plen | 4 | `crc_pkt` | 本包 offset 0 … 4+plen 的 CRC32 |

#### `flag`

中间片 `0x02`，最后一片必须 `0x03`。最后一片即使 `plen=232` 也要标 END，板端靠 flag 知道「可以做 `crc_file` 了」，不靠「凑满窗口 8」。

不要在 DATA 上发 `0x01`（START 只走 CTRL）。

#### `seq`

本片在 **JPEG 分片序列**里的编号，从 1 起。小端，例如 seq=9 写成 `09 00`。

- 必须与板端期望值一致，否则 `SEQ_ERR`（value=期望 seq）。
- 不要从 0 开始发 DATA（0 只给 START）。
- 不要跳号、不要重复；WWR 丢包后不要尝试只补一片，整图从 START 重来。
- 重传新 START 之后，seq 重新从 1 计。

#### `plen`

本包 payload 有多少字节，**不是**整图 `total_len`，也不是 241（那是整包长度）。

| 情况 | `plen` |
|------|--------|
| MIDDLE | 必须 **232**，不能短包 |
| END | `total_len % 232`；余数为 0 时填 **232** |
| 合法范围 | 1…232；END 不得为 0 |

填 0、填 244、填 `total_len`：都是 `SIZE_ERR`。

包总长 = `9 + plen`（5 字节头 + payload + 4 字节 CRC），MIDDLE 固定 **241**，≤ ATT 有效载荷 244。多出来的 3 字节余量不要自行加填充。

#### payload

JPEG 文件按顺序切开的原始字节，**不要**再包一层 JSON/Base64/十六进制字符串。BLE 写的是二进制。

- 第 1 片（seq=1）通常以 `FF D8` 开头（SOI，Start of Image）。
- 最后一片应覆盖到 JPEG 的 `FF D9`（EOI，End of Image）。
- 板端写入：`memcpy(buf + (seq-1)*232, payload, plen)`。
- 不要在 payload 里重复 magic、宽高、CRC。那些只在 START。

#### `crc_pkt`

覆盖本 DATA 包去掉最后 4 字节后的全部内容（flag+seq+plen+payload）。算法同 START 的包 CRC。每包单独算，不能复用 `crc_file`。

### 4.4 两层 CRC

| 层 | 字段 | 覆盖范围 | 何时算 | 失败码 |
|----|------|----------|--------|--------|
| 包 CRC | `crc_pkt` | 该包去掉最后 4 字节后的全部字段 | GATT 回调里立刻算 | `CRC_PKT` |
| 文件 CRC | `crc_file` | 完整 JPEG 文件（不含任何协议头） | 收齐 END 之后 | `CRC_FILE` |

BLE 链路层 CRC24 挡不住：WWR 丢包、seq 乱序、APP 组包错误。应用层 CRC 不能省。

`crc_pkt` 出错的包不写入缓冲。`crc_file` 失败则丢弃整图。

## 5. STATUS（Notify，固定 5 字节）

板 → 手机，使能 Notify 之后才会收到。固定 5 字节，不要当字符串解析。

| 偏移 | 长度 | 字段 | 编码 |
|------|------|------|------|
| 0 | 1 | `code` | uint8，结果类型 |
| 1 | 4 | `value` | uint32 LE，含义随 `code` 变 |

#### `code`

本协议只用下表。`0x03`～`0x0F`、`0x15`～`0x1F`、`0x21`～`0xFF` 未定义，APP 当失败并停发。不要把 `code` 理解成 HTTP 状态码。

| code | 名 | value 填什么 | value 不要填 | APP 行为 |
|------|----|--------------|--------------|----------|
| `0x00` | OK | 窗口大小，**固定 8** | 不要填 0 当「成功」；成功与否看 code 不是看 value | 开始发 DATA |
| `0x01` | BUSY | **0**（占位，无附加信息） | 不要填剩余秒数 | 上一张还在收/解码，稍后重发 START |
| `0x02` | RX | 板端 **下一个期望 seq**（例如收完 1…8 后填 9） | 不要填「本窗已收个数」 | 发下一窗，下一包 seq 必须等于这个 value |
| `0x10` | CRC_PKT | 出错那一包的 **seq** | 不要填 CRC 数值本身 | 整图从 START 重传 |
| `0x11` | CRC_FILE | **0** | 不要填算出来的 CRC（对 APP 没用，整图已丢） | 整图从 START 重传 |
| `0x12` | SIZE_ERR | 非法的那个长度或宽高（能填则填，否则 0） | — | 检查 360×360 / 降 JPEG 质量后重传 |
| `0x13` | SEQ_ERR | **期望的 seq** | 不要填收到的错误 seq | 整图从 START 重传 |
| `0x14` | FLAG_ERR | 收到的非法 flag（0～255，高 3 字节为 0） | 不要把 `'S'` 这种字符码当协议 flag 回传 | 检查是否把 flag 写成了字符；整图从 START 重传 |
| `0x20` | DONE | 本次 **`total_len`** | 不要填 1 当 true | 成功，QSPI 已换图 |

`value` 在 BUSY / CRC_FILE 里填 **0 的意思是「这个码没有额外参数」**，不是失败，也不是 seq=0。判断对错只看 `code`。

错误码（`0x10`–`0x14`）到达后，板端丢弃整图，回到空闲。APP 整图重传，建议最多 **3** 次。

超时：

- START 等 OK：**2 s**
- 一窗 DATA 等 RX：**2 s**
- END 等 DONE：**5 s**（含 JPEG 解码 + 刷屏）

## 6. 窗口与时序

```
APP                                         板
 |---- CTRL START (flag=0x01, 26B) -------->|  验 crc_pkt，PSRAM 分配 total_len
 |<----------- Notify OK (value=8) ---------|
 |---- DATA MIDDLE seq=1 .. 8 ------------->|  每包验 crc_pkt，memcpy
 |<----------- Notify RX  (value=9) --------|
 |---- DATA MIDDLE seq=9 .. 16 ------------>|
 |<----------- Notify RX  (value=17) -------|
 |                  ...                     |
 |---- DATA END   seq=chunk_cnt ----------->|  验 crc_file
 |<----------- Notify DONE -----------------|  LVGL 线程解码，刷 QSPI
```

发送规则：

1. START → 等 `OK`。
2. 连续最多 **8** 个 DATA（最后一窗可以不足 8）。
3. 停，等 `RX`，`value` 必须等于下一包 seq。
4. 最后一包 flag=`END`，发完等 `DONE`。
5. 任何错误码 → 停发，从 START 重来。

板端在以下时刻发 `RX`：

- 已收满 8 个 DATA，且还不是 END；
- 或收到 END（此时不再发 RX，改走 `crc_file` → `DONE` / `CRC_FILE`）。

## 7. APP 流程

1. 蓝牙权限、打开适配器。
2. 扫描 `XMZX-D126`，连接。
3. `requestMtu(247)`，发现 `FF00`，使能 `FF03` Notify。
4. 相册选图 → 缩放到 **360×360**（不足补边或居中裁剪，不要拉伸变形除非产品要求）→ JPEG quality **70–80**。
5. 若 `jpeg.length > 98304`，降低 quality 再压，直到 ≤ 96 KB。
6. `crc_file = CRC32(jpeg)`。
7. `chunk_cnt = ceil(jpeg.length / 232)`。
8. 组 START，Write Request 到 CTRL，等 `OK`。
9. 按 232 字节切片：
   - 非最后一片：`flag=MIDDLE`，`plen=232`
   - 最后一片：`flag=END`，`plen=剩余`
   - 每包算 `crc_pkt`，WWR 到 DATA
   - 每 8 包（或遇到 END）停等 STATUS
10. 收到 `DONE` 显示成功；错误则整图重传，最多 3 次。

GATT 回调（手机 Notify 回调）里不要做重活；组包、压缩在业务线程。

## 8. SDK 流程（对照，APP 不实现）

1. `AIC_USING_UART3=y`，`LPKG_BT_UART="uart3"`，`aicbt_init()`。UART3 无封装脚，**不要 pinmux**。
2. 广播 `XMZX-D126`，注册三个 Characteristic。`CONFIG_BT_L2CAP_TX_MTU=247`，ACL RX ≥ 251。
3. 状态机：`IDLE → WAIT_DATA → WAIT_DEC → IDLE`。
4. GATT 回调只做：拆包、`crc_pkt`、seq 检查、`memcpy` 进 PSRAM。禁止在回调里调 VE 或刷屏。
5. END 且收齐：算 `crc_file` → 消息给 LVGL 线程 → `lv_disp_set_default(qspi_disp)` → `lv_aic_stream_open_buf()` / `lv_mpp_dec` → `lv_img_set_src()`。
6. 同时播 MIPI mp4 时 VE（Video Engine，硬件编解码）可能忙，回 `BUSY` 或排队，不要在 BLE 线程死等。

双屏、`qspi1`、`ui_init`、pinmux 不因本协议改动。

## 9. CRC 计算约定

覆盖范围 **不含** 最后 4 字节的 `crc_pkt` 本身。

伪代码：

```
crc_pkt  = crc32(packet[0 .. packet.length-5])   // 含 flag/seq/plen/payload 或 START 前 22 字节
crc_file = crc32(jpeg[0 .. total_len-1])         // 纯 JPEG，无协议头
```

空缓冲区的 CRC32（ISO-HDLC）为 `0x00000000`（init 全 1 再 xorout）。本协议 `total_len` 最小为 1，不会出现空文件。

## 10. 非法包判定（板端）

| 条件 | 码 |
|------|----|
| `crc_pkt` 不匹配 | `CRC_PKT` |
| START 的 magic ≠ `IMGP` | `FLAG_ERR` |
| `width/height` ≠ 360，或 `fmt` ≠ 0 | `SIZE_ERR` |
| `total_len` 为 0 或 &gt; 98304 | `SIZE_ERR` |
| `chunk_cnt` ≠ `ceil(total_len/232)` | `SIZE_ERR` |
| MIDDLE 的 `plen` ≠ 232 | `SIZE_ERR` |
| END 的 `plen` 与剩余字节不符 | `SIZE_ERR` |
| `seq` 不是下一个期望值 | `SEQ_ERR` |
| flag 不是 0x01/0x02/0x03，或出现顺序错误（未 START 就 DATA、START 后再 START 等） | `FLAG_ERR` |
| 非空闲时又收到 START | `BUSY` |
| 整图 CRC 不符 | `CRC_FILE` |

## 11. 包示例

假设 JPEG 500 字节。

```
chunk_cnt = ceil(500 / 232) = 3
窗 1：MIDDLE seq=1 plen=232
     MIDDLE seq=2 plen=232
     END    seq=3 plen=36     ← 本窗不足 8，END 后不再等 RX，等 DONE
```

START hex 布局（数值示例，CRC 需按真实 JPEG 计算）：

```
01                  flag START
00 00               seq = 0
49 4D 47 50         "IMGP"
F4 01 00 00         total_len = 500
68 01               width = 360
68 01               height = 360
00                  fmt JPEG
03 00               chunk_cnt = 3
xx xx xx xx         crc_file
yy yy yy yy         crc_pkt
```

## 12. 双方分工

| 侧 | 做 | 不做 |
|----|----|------|
| APP | 扫连、压 360×360 JPEG、按窗口发 START/MIDDLE/END、解析 STATUS | 屏驱、pinmux、解码 |
| SDK | 从机、收包状态机、两层 CRC、PSRAM 组图、LVGL 线程解码刷 QSPI | 选图、压缩、手机 UI |
| 协议 | 本文全部数值与包格式 | 仓库其余模块 |

本文是 APP 与 SDK 的唯一对照件。改 MTU、窗口、负载、UUID、STATUS 码必须两边同步改版本号。
